# launch

`gosuda.org/hqq/launch` starts an HQQ server (a C program built on libhqq:
`hqq-sqlite-server`, a server generated by `hqq-bindgen`, ...) as a child
process, verifies the binary before it runs, ties the server's life to the
process that started it, and waits until it serves. It knows nothing about the
service: the server's own options are the caller's arguments.
[`sqlite/launcher`](../sqlite/launcher/README.md) is the SQLite layer on top of
it.

```go
l, err := launch.NewListenerName("myapp") // myapp-<12 hex digits>
if err != nil {
    return err
}
srv, err := launch.Start(ctx, launch.Config{
    Binary:   "/opt/hqq/bin/myapp_server",
    SHA256:   want,        // secureexec.ParseHash("9f86d08..."), 64 hex digits
    Listener: l,           // the name in the ready line
    Args:     []string{l}, // the listener is the server's first argument
}, "--max-sessions", "64") // more arguments, after the lifeline flag
if err != nil {
    return err
}
defer srv.Close()
// connect to srv.Listener()
```

A signed release manifest replaces `Binary` and `SHA256`:

```go
srv, err := launch.Start(ctx, launch.Config{
    Manifest: &launch.ManifestSource{
        Data: data, Signature: sig, // manifest.json and manifest.json.sig
        PublicKey: pub,             // required: this package embeds no key
        Dir:       "/opt/hqq/dist",
    },
    Listener: l,
    Args:     []string{l},
})
```

`Start` checks the signature before it parses the manifest, selects the entry
for `runtime.GOOS` and `runtime.GOARCH` (`ErrNoArtifact` when there is none), and
verifies the file named by that entry in `Dir`.

## What it verifies

`Start` runs the server only after `secureexec.Verify` has hashed the bytes that
will be executed: a path swap or an in-place overwrite between the check and the
exec does not change what runs. The mechanism per platform and its limits are in
`secureexec/README.md`. Root attackers, kernel compromise and a compromised
expected digest are out of scope.

`Start` never runs a binary without an expected digest: a `Config` with neither
`SHA256` nor `Manifest` returns `ErrConfig`, and so does one with both.

## Process contract

The server follows the contract of the C servers (`examples/sqlite/server/README.md`):

- The command line is `Config.Args`, the lifeline flag, then the arguments of
  `Start`. The listener name is not added: put it where the server expects it.
  The trailing arguments follow the flag so that a `--` among them cannot turn
  the flag into an operand.
- The ready line is `ReadyPrefix + Listener + "\n"` (`ready <listener>\n`) on
  stdout, exactly. Another line, a longer name or a missing newline is not it.
- The lifeline flag is `--parent-stdin` (`DefaultLifelineFlag`); `LifelineFlag`
  changes it, for example to `--parent-stdin=force`. The server reads its
  standard input to end of file and shuts down gracefully when it comes.
- On Unix the server also stops on `SIGTERM`; on Windows on `CTRL_BREAK`.

## Lifecycle

- `Start` returns when the ready line arrives. The line is consumed. Everything
  else on stdout and stderr goes to `Config.Stdout` and `Config.Stderr`, which
  are optional; their errors are ignored. The last 2 KiB of output appear in
  error messages (1 KiB of it in the message text, all of it in the `Output`
  field of `*StartError` and `*ReadyTimeoutError`).
- `ctx` bounds only the start. A canceled or expired `ctx` kills the server and
  returns a `*StartError` that wraps the context error. The server keeps running
  after `Start` returns.
- `ReadyTimeout` (default 10 s) kills the server and returns `*ReadyTimeoutError`
  (`errors.Is(err, ErrReadyTimeout)`). A server that exits before it is ready
  returns `*StartError` wrapping its exit status.
- A verification failure returns `*StartError` whose `Err` wraps
  `secureexec.ErrHashMismatch` (or `ErrNotRegular`, `ErrUnsupported`). No process
  is started.
- Unless `DisableLifeline` is set, the parent keeps the write end of a pipe on
  the server's stdin. The server shuts down gracefully when the parent exits for
  any reason, including SIGKILL, because the kernel closes the parent's
  descriptors. `DisableLifeline` omits the flag; `Stop` then sends `SIGTERM`
  (`CTRL_BREAK` on Windows).
- `Stop(ctx)` closes the pipe and waits up to `StopTimeout` (default 10 s) for a
  graceful exit. It returns the exit status error (nil for status 0). After
  `StopTimeout`, or when `ctx` ends, it kills the server and returns
  `ErrStopTimeout` (or the context error). `Close` is `Stop` with no caller
  deadline, and both are idempotent.
- `Done` closes when the process has exited. `Err` returns the exit status error
  after that, and nil while the server runs.
- The verified snapshot is released when the process exits.
- `Env` is the server's whole environment (nil inherits the caller's); `Dir` is
  its working directory.

## What it does not do

- No restart and no supervision: when the server exits, `Done` closes and the
  caller decides what to do.
- A server that is stopped (SIGSTOP, a debugger) rather than dead keeps the pipe
  open and keeps running. The same holds for any other process that inherits the
  write end; `os.Pipe` is close-on-exec, so only processes that deliberately
  inherit it can hold it.
- The server must not fork and keep running: the lifeline thread does not exist
  in a fork child.
- `Stop` and the kill signal target the server process only, not its children.
- It does not choose or validate the server's own options, and it does not
  connect to the server.

## Tests

`go test ./launch/...` runs against a stub server (the test binary,
re-executed, `internal/launchtest`): hash ok and mismatch, manifest accepted,
bad signature, tampered manifest, missing platform, signed digest that does not
match the file, ready timeout, lines that are not the ready line, exit before
ready, canceled start, graceful and forced stop, crash status, output capture
and tail, command line, `DisableLifeline` and `LifelineFlag`, `Env`, `Dir`, and
the lifeline closing when the parent is killed. Tests against the real C server
are in `sqlite/launcher`.
