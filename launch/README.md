# `launch`

Package `gosuda.org/hqq/launch` starts an HQQ server (any C binary built on [`libhqq`](../c/README.md), such as [`hqq-sqlite-server`](../bindgen/examples/sqlite3/README.md) or any server generated by [`hqq-bindgen`](../bindgen/README.md)) as a supervised child process. Before executing the binary, `launch` verifies its cryptographic digest via [`secureexec`](../secureexec/README.md), binds the server's lifetime to the parent process over a standard-input lifeline pipe, and waits until the server prints its readiness line on standard output.

The `launch` package is service-agnostic: caller-supplied flags are forwarded directly to the child process, and [`sqlite/launcher`](../sqlite/launcher/README.md) layers SQLite-specific flags and `database/sql` registration on top of it.

```go
l, err := launch.NewListenerName("myapp") // myapp-<12 hex digits>
if err != nil {
    return err
}
srv, err := launch.Start(ctx, launch.Config{
    Binary:   "/opt/hqq/bin/myapp_server",
    SHA256:   want,        // secureexec.ParseHash("9f86d08..."), 64 hex digits
    Listener: l,           // the name expected in the ready line
    Args:     []string{l}, // the listener is the server's first argument
}, "--max-sessions", "64") // extra arguments placed after the lifeline flag
if err != nil {
    return err
}
defer srv.Close()
// connect to srv.Listener()
```

When distributing multi-platform release bundles, a signed release manifest can replace `Binary` and `SHA256`:

```go
srv, err := launch.Start(ctx, launch.Config{
    Manifest: &launch.ManifestSource{
        Data:      data, // manifest.json bytes
        Signature: sig,  // manifest.json.sig text
        PublicKey: pub,  // required: this package embeds no key
        Dir:       "/opt/hqq/dist",
    },
    Listener: l,
    Args:     []string{l},
})
```

When `Manifest` is configured, `Start` verifies the Ed25519 detached signature before parsing the JSON manifest, selects the entry matching `runtime.GOOS` and `runtime.GOARCH` (returning `ErrNoArtifact` if absent), and verifies the corresponding binary inside `Dir`.

## What It Verifies

`Start` executes the server binary only after `secureexec.Verify` has hashed the exact file image that the kernel will map and execute. Neither a directory path swap nor an in-place file overwrite between verification and execution can alter the code that runs. Platform-specific mechanisms (`memfd` with file sealing on Linux, `0700`/`0500` temporary vaults on macOS and BSD, and share-locked handles on Windows) and their threat boundaries are detailed in [`secureexec/README.md`](../secureexec/README.md). Root-level attackers, kernel compromise, and compromised expected digests are outside the threat model.

`Start` refuses to execute an unverified binary: passing a `Config` with neither `SHA256` nor `Manifest` returns `ErrConfig`, as does passing both simultaneously.

## Process Contract

Child binaries launched by `Start` must implement the standard HQQ C server contract (implemented by `hqqrpc_main` and documented in [`bindgen/examples/sqlite3/README.md`](../bindgen/examples/sqlite3/README.md)):

- **Command-line layout**: The child command line consists of `Config.Args`, followed by the lifeline flag, followed by any trailing arguments passed to `Start`. `launch` does not inject the listener name into `Args` automatically; callers place `Listener` in `Config.Args` at the position the target binary expects. Trailing arguments are placed after the lifeline flag so that a `--` separator in the caller's trailing arguments cannot turn the lifeline flag into a positional operand.
- **Readiness line**: Once the acceptor is listening in shared memory, the server must write `ReadyPrefix + Listener + "\n"` (`ready <listener>\n`) to standard output and flush the stream. Partial lines, mismatched listener names, or missing newlines are rejected.
- **Parent-stdin lifeline**: The default lifeline flag is `--parent-stdin` (`DefaultLifelineFlag`), which can be overridden via `Config.LifelineFlag` (for example, `--parent-stdin=force`). When this flag is present, the server monitors its standard input and initiates a graceful shutdown as soon as `stdin` reaches `EOF`.
- **Termination signals**: On Unix, the server also initiates a graceful shutdown on `SIGTERM` (and `SIGINT`). On Windows, it stops on `CTRL_BREAK`.

## Lifecycle

Each `*Server` handle returned by `Start` progresses through a deterministic startup, steady-state, and teardown lifecycle:

- **Readiness and output capture**: `Start` blocks until the readiness line arrives on `stdout` and consumes that line. All subsequent bytes on `stdout` and `stderr` (as well as any lines emitted before the readiness line) are forwarded to `Config.Stdout` and `Config.Stderr` if configured; write errors on those sinks are ignored. The most recent 2 KiB of combined output is retained in a ring buffer so startup failures can include diagnostic context (up to 1 KiB in `.Error()` text, and the full 2 KiB in the `Output` field of `*StartError` and `*ReadyTimeoutError`).
- **Startup context**: The `ctx` passed to `Start` bounds only the startup handshake. If `ctx` is canceled or expires before the readiness line arrives, `Start` kills the child process and returns a `*StartError` wrapping `ctx.Err()`. Once `Start` returns, canceling that startup `ctx` has no effect on the running server.
- **Readiness timeout and early exit**: If the server does not emit its readiness line within `ReadyTimeout` (default `10s`), `Start` kills the child process and returns `*ReadyTimeoutError` (matching `errors.Is(err, ErrReadyTimeout)`). If the child process exits before emitting the readiness line, `Start` returns `*StartError` wrapping the process exit status.
- **Verification errors**: If binary verification fails, `Start` returns a `*StartError` wrapping `secureexec.ErrHashMismatch`, `secureexec.ErrNotRegular`, or `secureexec.ErrUnsupported` without spawning a child process.
- **Lifeline pipe**: Unless `DisableLifeline` is set, the parent process holds the write end of an `os.Pipe` connected to the child's `stdin`. If the parent process terminates for any reason (including an untrappable `SIGKILL`), the operating system kernel closes the parent's file descriptors, delivering `EOF` to the child's `stdin` and triggering an orderly server shutdown. Setting `DisableLifeline: true` omits the lifeline flag and relies on `SIGTERM` (`CTRL_BREAK` on Windows) during `Stop`.
- **Graceful and forced stop**: `Stop(ctx)` closes the lifeline pipe (or sends the stop signal when `DisableLifeline` is set) and waits up to `StopTimeout` (default `10s`) or `ctx.Done()` for the server to exit cleanly. If the server exits with status `0`, `Stop` returns `nil`. If the deadline expires first, `Stop` forcibly kills the process and returns `ErrStopTimeout` (or `ctx.Err()`). `Close()` is shorthand for `Stop(context.Background())`, and both `Stop` and `Close` are idempotent.
- **Completion notification**: `srv.Done()` returns a channel that closes when the child process exits. After `Done()` closes, `srv.Err()` returns the process exit error (`nil` for exit status `0`); while the server is still running, `srv.Err()` returns `nil`.
- **Snapshot cleanup**: The verified executable snapshot created by `secureexec` is released automatically when the child process exits.
- **Environment and working directory**: `Config.Env` specifies the complete child environment (`nil` inherits the parent's environment), and `Config.Dir` sets the child's working directory.

## Scope Boundaries

The `launch` package intentionally keeps process supervision minimal and predictable:

- **No automatic restarts**: When the child process exits, `Done()` closes and the caller decides whether to restart or propagate the failure.
- **Stopped processes**: A parent process suspended by `SIGSTOP` or a debugger is not dead; its file descriptors remain open in the kernel, so the server continues running. Similarly, any grandchild process that explicitly inherits the write end of the lifeline pipe keeps it open (`os.Pipe` sets `O_CLOEXEC`, so normal `exec` calls do not leak the descriptor).
- **No daemonizing forks**: The server binary must not `fork()` and continue serving in the child, because the parent-stdin reader thread is not duplicated across `fork()`.
- **Single-process signaling**: `Stop` and forced kills target only the direct child process, not a process group or descendants.
- **No client attachment**: `launch` neither validates service-specific flags nor opens an HQQ client link; callers connect to `srv.Listener()` using the appropriate client package.

## Running the Tests

The unit test suite in `launch` exercises every lifecycle and verification path against a self-re-executed test helper (`internal/launchtest`):

```bash
go test -race -count=1 ./launch/...
```

Covered scenarios include valid and mismatched SHA-256 hashes, valid and tampered signed manifests, bad Ed25519 signatures, missing platform entries, ready timeouts, non-ready preamble lines, early exits before readiness, canceled startup contexts, graceful and forced stops, non-zero crash statuses, stdout/stderr capture and 2 KiB tail truncation, command-line ordering, `DisableLifeline` and custom `LifelineFlag`, `Env` and `Dir` propagation, and automatic child shutdown when a parent process is killed with `SIGKILL`. End-to-end tests against the compiled C `hqq-sqlite-server` live in [`sqlite/launcher`](../sqlite/launcher/README.md).
